# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

chartmaker renders a raid timeline chart as a PNG: one column per player, one pixel per second over a 60-minute window. It shows each boss battle, the 5-minute cooldown, the floor level, and the expected score. All logic lives in `ChartLib.py`. `time_chart.ipynb` is the driver. There is no build system or linter. `tests/` holds a pytest suite (see Tests). `requirements.txt` lists the dependencies for the browser GUI (see below).

## Running

Run the notebook cell in `time_chart.ipynb`. It uses Python 3.10. The equivalent code is:

```python
import json
from ChartLib import generate_chart
generate_chart("./src/<name>.txt", "./output/<name>.png", json.load(open("config.json")))
```

- Run it from the repo root. `ChartLib` defines `BASE_DIR` as its own directory (`app.py` imports it from there), and every asset path (fonts, images, logo) is `BASE_DIR` + a path that starts with `/`.
- `src/` (input schedules) and `output/` are not tracked by git, so create them locally. `output/` is only the destination of the notebook's PNGs.
- Dependencies: `opencv-python`, `numpy`, `Pillow`. Pillow is pinned to the major version the golden images were checked with (`>=12,<13`). Text width uses `textbbox(...)[2]`, which equals the old `textsize` width, so the output matches Pillow 9.5 pixel for pixel. OpenCV must be **< 5**: OpenCV 5 replaced the Hershey fonts in `putText` and ignores `thickness`, which changes the typeface and removes the text outlines (the thick `bgcolor` underlay).

```sh
.venv/Scripts/python -m pytest
```

- `test_app.py`: the Flask API through the test client, including the tracker's kill/undo rules (409s) and the Discord notify/clear/pause/discard flow and `GET .../text` (`send_discord` and `delete_discord` are monkeypatched, so nothing reaches Discord). It imports `app` with `STORE` and `PLAN_BUCKET` unset, so it uses `MemoryStore` and saves nothing.
- `test_archive.py`: the Cloud Storage file names and the per-prefix daily sequence, against a fake bucket.
- `test_store.py`: version bumps, the 5h expiry (never extended), `CachedStore` reuse, and `delete`.
- `test_chart_image.py` renders `tests/fixtures/plan_full.txt` (all display flags, short and long battles, rates < 1, 11 floors) and `plan_plain.txt` (no flags, `display_remaining`), and compares them with `tests/golden/*.png` pixel for pixel. On a mismatch, it writes the actual image and a copy with the differing pixels painted red to pytest's tmp dir. After an intended drawing change, check the images by eye, then run with `UPDATE_GOLDEN=1` to rewrite the goldens. Run this test before bumping Pillow or OpenCV.
- The fixtures use fictional players. Never put real plans from `src/` (real player names) into `tests/`.
- `tests/` and `requirements-dev.txt` are excluded from the container (`.dockerignore`).

## Browser GUI (`app.py` + `web/`)

```sh
py -3.11 -m venv .venv
.venv/Scripts/pip install -r requirements.txt
.venv/Scripts/python app.py        # http://127.0.0.1:5000 (override with PORT)
```

- `app.py` is a thin, stateless Flask wrapper. It never modifies ChartLib's behaviour. Endpoints:
  - `GET /logo.png` serves the root `logo.png` for the GUI header. It is the same file as config.json's `logo_image`, which is drawn into the chart.
  - `GET /icon.png` serves the root `icon.png` as the browser-tab favicon. The page title is "ChartMaker".
  - `GET /robots.txt` disallows `/tracker` (the session id is the only access control) and `/api/` for crawlers. The editor and `/guide` stay crawlable.
  - `GET /image/<name>` serves a boss icon from `image/`, for the GUI thumbnails.
  - `GET /guide` serves `web/guide.html`, the user guide (Japanese, static, self-contained CSS). The editor toolbar, the empty-plan `#guide` card and the tracker header link to it (the tracker to `/guide#tracker`).
  - `GET /api/site` returns `{support_url}` from the `SUPPORT_URL` env var (only `https://` URLs; otherwise empty). `web/common.js` fetches it and unhides the `#support-link` ("♡ 開発を支援", the donation link) in the editor and tracker headers.
  - `GET /api/config` returns config.json and the list of `image/*.png` (as `/image/<name>` paths).
  - `POST /api/parse {text}` returns `ChartLib.parse`.
  - `POST /api/detail {text}` returns `generate_detail`, which the GUI uses for Lv/score.
  - `POST /api/render {text}` writes the txt to a temp dir and calls `generate_chart`, returning a PNG. When `PLAN_BUCKET` is set, it then saves the txt to that Cloud Storage bucket as `plans/YYYYMMDD_<seq>_<Max>_<Est>.txt` (`archive.py`; JST date, a 3-digit sequence per day, the chart footer's Max/Est totals). A failed save is only logged. Without `PLAN_BUCKET` (local runs) nothing is saved.
  - Validation errors are returned as 400 `{error}`.
- `web/app.js` (vanilla JS, no build step) stores each action as an absolute start second. It converts back to relative `wait_seconds` in `toText()`, and the output must stay parseable by `parse`. `toText()` always writes the rate, even 1, with at least 2 decimals (`rateText`: `0.00`, `0.50`, `0.65`, `0.777`, `1.00`; longer decimals are not rounded), so every action line has at least 5 fields.
- Shared constants: `ChartLib.py` defines `BOSSES`, `REGULAR_BOSSES`, `IMAGE_KEYS`, `COOL_TIME` and `MAX_PLAYERS`, and `app.py` imports them. The browser side cannot import Python, so `web/common.js` mirrors `BOSSES`, `BOSS_LABEL`, `COOL_TIME` and `CHART_SEC` and is loaded before `app.js` and `tracker.js`. Keep the two in sync. Top-level `const`s in these classic scripts share one scope, so never redeclare a `common.js` name.
- Image file names are internal and are never shown in the UI. In the settings panel, each boss's current image appears as a thumbnail only. Clicking it opens a thumbnail grid (`openImagePicker`) that has no file names, tooltips, or filter. The thumbnails imitate the chart: CSS `object-fit: cover` crops the centre square, and the background shows the boss element color, or `icon_bgcolor` if it is set. A boss image that is not in `IMAGES` (the server's `image/*.png`) is replaced with `/image/blank.png` by `fixImages`, both on import (`stateFromParsed`, so txt files and share URLs) and when the `localStorage` draft is restored.
- Each timeline block shows at most 3 lines, so it still fits at the smallest zoom (0.15 px/sec, a block about 45 px tall). Line 1 is the battle's start–end time in bold. Line 2 is the boss, the battle seconds, and the rate when it is below 100%. Line 3 is the Lv and score from `/api/detail`. The block's bottom right shows the cool-off time `clock(start + blockLen())` (`.cool-off`, the block's lower edge = the chart's `cool_off`) only when it doesn't overlap those lines (`INFO_LINE` = 13 px, the info `line-height`), so it is hidden at 0.15 and shown from 0.25 up.
- Players cannot be added or removed. The editor always has exactly `MAX_PLAYERS` (20) columns: `fillPlayers` pads `defaultState`, `stateFromParsed` and the restored `localStorage` draft with empty players `P01`, `P02`, … (skipping used ids). Columns can still be renamed (name/ID) and moved left/right. `toText()` writes only players that have a name (`::ID=name`) or battles, so empty columns don't reach the txt. On import, `::P01=name`-style keys (`DEFAULT_ID`) also count as players. Imported players fill the columns in parse order (players with battles first), so the position of an empty column between used ones is not kept.
- Per-player score: `playerScores` sums each column's `score`/`est_score` from `details` (null while out of sync), as in the chart footer. `render()` adds a line to each column header with the est score (colored like the footer: `estimate_score` when est < max, else `max_score`; max and sortie count in the `title`) and a thin bar scaled to the top player's est (`.pscore`, `.pbar`; the header is 66 px tall). With a column selected, the side panel shows est/max, the share of the total and the sortie/Realm counts.
- Double-clicking an empty spot in a column adds a battle there (`addActionAt`). While the plan has no battles, `#guide` (a card over the timeline, sticky and `pointer-events: none` so the double-click still reaches the column) says so; `render()` hides it once any battle exists. The side panel's default hint also starts with it.
- The `#guide` card also has サンプルを開く (`openSample`), which fetches `web/sample.txt` (`/static/sample.txt`, fictional players only, with a locked battle that has an inline note, and two range notes) and loads it through `importText` (one undo step; confirm first if the plan has battles). `test_sample_plan` checks that it parses and that its notes are accepted by `POST /api/sessions`.
- **Keep the user guide current.** `web/guide.html` explains how the tool works (not the game rules) for first-time users. Whenever a user-visible feature is added or its behaviour changes (editor, auto build, stats, share, tracker, personal view, Discord, storage or expiry), update the matching section of `guide.html` in the same change, and update `web/sample.txt` if the new feature should be showcased.
- Saved files are named after today's date: `YYYYMMDD.txt` from the text panel and `YYYYMMDD.png` from the image preview (`dateStem()`).
- Image preview (`#modal`) extras. `renderImage` keeps the PNG in `previewBlob` for both of these:
  - 画像をコピー (`copyPreviewImage`) writes it to the clipboard with `ClipboardItem`, so it can be pasted into Discord with Ctrl+V.
  - Discord に投稿 (`openPostDialog`, `postToDiscord`, `#post-dialog`) posts it to a Discord webhook straight from the browser. Discord allows CORS on webhooks, so the server is not involved and never sees the URL.
    - The URL must match `POST_WEBHOOK`, a mirror of `app.py`'s `DISCORD_WEBHOOK` that also allows a query such as `?thread_id=`.
    - It is remembered in `localStorage` (`chartmaker.post.webhook`; prefilled from the tracker's `chartmaker.tracker.webhook`). The checkboxes are remembered in `chartmaker.post.opts`.
    - The request is multipart: `payload_json` = `{content, allowed_mentions: {parse: []}}`, `files[0]` = `YYYYMMDD.png`, and optionally `files[1]` = `toText()` as `YYYYMMDD.txt`. It is sent with `?wait=true` so errors come back.
    - `content` is the optional message plus, when checked, `discordLink(shareUrl())`. Over 2000 characters it is refused with a hint to drop the link and attach the txt.
- The `»` at the right end of the side panel's tabs (`#side-hide`, not a `data-tab` button, so tab code selects `.tabs button[data-tab]`) hides the side panel and the splitter (`body.side-hidden`, `setSideHidden`); while hidden, a thin `« パネル` strip (`#side-show`) on the right edge of `main` shows it again. The state is remembered in `localStorage` (`chartmaker.sideHidden`). Block and column clicks keep it hidden; only `switchTab(name, true)` (the note band on the axis) shows it again.
- Undo/redo (Ctrl+Z / Ctrl+Y) keeps state snapshots. The working state is autosaved to `localStorage` in the browser only.
- Changing a block's boss without the settings panel: right-click a block to rotate it 1st → 2nd → 3rd → Realm → 1st, or press `1`–`4` with a block selected to set it directly. Each change is one undo step.
- `↑`/`↓` move the selected block by 1 s (`Shift` = 10 s) through `slideTo`, so pushes and locks behave as in a drag (`nudge`). Presses on the same block less than 1 s apart, with no other change in between, merge into one undo step. A press that moves nothing is ignored.
- Multi-select (stage 1):
  - `Ctrl`+click adds or removes a block. `Shift`+click selects the rectangle between the anchor and the clicked block (`rangeSelect`): in every column from the anchor's to the clicked one, the blocks whose start lies between the two blocks' starts (in one column, every block between them). `Ctrl`+`A` (`selectAll`) selects every block. `Esc` or pointerdown on an empty column area clears the selection. A plain click or drag selects one block.
  - State: `multi` holds `[{p, a}]` only when 2+ blocks are selected. `selection` stays a block, which is the Shift anchor. Always change the selection through `setSelection`, and read it through `selectedBlocks()`.
  - Boss changes (1–4 keys, right-click, panel), lock (`L` locks all if any is unlocked, otherwise unlocks all), battle seconds, rate, and delete apply to every selected block. Empty "混在" (mixed) fields are ignored.
  - Group move (`shiftSelected`): dragging a selected block or pressing `↑`/`↓` shifts every selected block by the same seconds, keeping their spacing, and pushes unselected blocks like `slideTo`. The shift is clamped so that no selected block passes a lock or the chart edge (one stopping stops all), and a selection that contains a locked block does not move. Releasing a selected block without moving selects it alone. The panel hides the start/wait inputs while several blocks are selected.
- timelag: the settings panel's 全般 has a `timelag(秒)` field (0–`MAX_TIMELAG` = 30). It is `::timelag` in the txt. A new plan (`defaultState`) starts at `DEFAULT_TIMELAG` = 1; imported txt without `::timelag` still falls back to `config.json` (0), so ChartLib and the goldens are unchanged. Collisions use `blockLen()` = timelag + 300, so with timelag 2 a 2 s gap after the cooldown already counts as touching. `setTimelag` (one undo step) keeps every start and pushes later blocks of the same player that are now closer than `blockLen()` (locked blocks too).
- Drag snap: while a block is dragged (alone or as a multi-selection, where the grabbed block is the reference) or added with a double-click, its start (push_start) snaps to the nearest candidate within `SNAP_PX` (5 screen px, so the width in seconds follows the zoom). Holding `Alt` turns it off. `↑`/`↓` never snap; resize snaps the battle end (below). The candidates are computed once at drag start by `snapCandidates`, which ignores the dragged/selected blocks and uses `simulateFloors` (a JS mirror of `calc_level`):
  - A 1st/2nd/3rd block snaps to the start of any 1st/2nd/3rd block in another column (a simultaneous sortie), and to each floor's Realm kill + `snapMargin` (the next floor has opened; at least +1 s even with margin 0, because `calc_level` needs `push_start >` the kill).
  - A Realm block snaps to the latest of the floor's 1st/2nd/3rd kill times (each the earliest `battle_end` on that boss, as in `calc_level`) + `snapMargin`.
  - Any block also snaps to 1 s below the nearest block above it in its own column that is not being moved (`above`: that block's start + `blockLen()` + 1), so moving it up can stop 1 s short of pushing. For a double-click add, `above` is the block before the insertion point.
  - Resize (the battle seconds, dragging the block's lower edge) snaps the battle end (`start + timelag + battle`) to `endSnapCandidates`: the `battle_end` of every block in another column (blocks ending at the same second merge into one candidate, so all of them are outlined) and `CHART_SEC`. The battle seconds stay clamped to 1–`MAX_BATTLE`; when the clamp stops it short, nothing is shown. `Alt` turns it off as well.
  - `snapMargin` (default `SNAP_MARGIN` = 6 s, 0–60) is set in the settings panel (スナップの余裕). It is an editor preference saved with `scale` in the `localStorage` draft, never written to the txt. Simultaneous-sortie candidates get no margin.
  - While snapped, `snapGuide` makes `render()` draw a line across all columns (`.hline.snap`) and outline the blocks it came from (`.snap-src`), and the drag tip names the reason. Nothing is shown when a lock or the chart edge stops the block short of the target.
- Timeline drag works like a sliding puzzle. A block moves alone through gaps and pushes touching neighbours. Pushed blocks stay where they were pushed.
- A block can be locked (`L` key or the checkbox in the side panel; shown with 🔒 and a dashed border). `slideTo` never moves a locked block, and pushes stop in front of it. The GUI state holds it as `locked: true` on the action. `toText()` writes it as a trailing `,lock` field on the action line (see the input format), which `parse` drops, so the chart is unchanged. `importText` reads it back from the raw text with `marksInText` (because `/api/parse` returns only the first 5 fields): the inline `lock`, or a legacy `#lock` comment line, which locks the most recent action line, counted per player in the same way as `parse`. A `#lock` line wins over an inline `unlock`. To lock or unlock the whole plan, the settings panel's 全般 has すべてロック / すべて解除 (`renderLockAll`, `setLockAll`, one undo step each, with the locked/total count), or `Ctrl`+`A` then `L`.
- Notes (注意点, shared cautions for the actual battle). Two kinds, both kept in the txt as `#` comment lines, so `parse` and the chart PNG are unchanged (notes are never drawn):
  - Battle note: `action.note` in the state, written by `toText()` as a trailing field after `lock`/`unlock` on the action line (`…,unlock,<text>` when not locked). A legacy `#note <text>` line right after the action line is still read and overrides the inline note. Edited in a textarea (`maxlength` `NOTE_MAX` = 200) in the side panel when exactly one block is selected (not in multi-select). A block with a note gets 📝 at the end of info line 2 and the note in its `title`.
  - Range note: `state.notes = [{start, end, text}]` in plan-elapsed seconds (0–3600, start < end, independent of `display_remaining`), written as `#note@<start>-<end> <text>` lines after the constants, before the action lines. Edited in the settings panel's 全体の注意点 list (start/end use `clock()`/`parseTime` like the push-time input; at most `MAX_NOTES` = 50). The timeline axis shows each range as a thin pink `.note-band`.
  - Text is one line (`noteText` collapses whitespace and cuts to 200 chars). Empty notes are not written. `marksInText` reads the inline lock/note (`splitAction`, a JS mirror of `ChartLib.split_action`), `#lock`, `#note` and `#note@` back from the raw text in `importText`, counting action lines like `parse`. `app.py` mirrors the rules in `parse_notes` (with `split_action`) and must stay in sync.
- Share URL (`共有URL` button, `copyShareUrl`): `encodePlan` packs the state into bytes with `encodeState` (only what `toText()` writes: varints, length-prefixed UTF-8 strings, boss colors as an index into `SHARE_COLORS`, `/image/<x>.png` stored as `<x>`, flags as a bitmask over `SHARE_FLAGS`, then the battles column by column: waits, a boss/rate/lock/note byte, battle seconds, rates, notes), compresses it with `CompressionStream("deflate-raw")`, base64url-encodes it, and puts it in the hash as `/#p=<code>` (about 45% shorter than the text). It checks that `toText(decodeState(...))` gives back exactly `toText()`, and otherwise falls back to the old `/#plan=<code>` (the txt itself, deflated). `SHARE_COLORS`/`SHARE_FLAGS` are part of the format: only append to them, and bump `SHARE_VERSION` for any other format change. `decodePlan` reads both forms, so old `#plan=` links keep working. 共有URL copies the plain URL. The `Discord用` button next to it (`#btn-share-discord`, same `copyShareUrl(btn, true)`) copies it as a Discord markdown link `[<comment>](<url>)` (`discordLink`: `[`, `]`, `\` in the comment are escaped with `\`; an empty comment becomes `作戦`). The hash never reaches the server, so the server stays stateless and stores nothing. On load (and on `hashchange`), `loadSharedPlan` removes the hash with `history.replaceState`, decodes it to txt, and imports it through `importText` (one undo step). It asks for confirmation first only when the current draft has battles and differs from the shared plan. A broken code shows an error in `#status`.
- Auto build (`自動作成 β` button, `web/auto.js`, loaded after `app.js`; its top-level names start with `auto`/`AUTO_`). It runs entirely in the browser. The server is unchanged and only sees one `/api/detail` call to verify the result.
  - The dialog (`#auto-dialog`) lists the players that have a name (`autoPlayers`). If none has a name, it uses the first `count` columns (`#auto-count`, default 20, saved with the settings) under temporary names `プレイヤー01`, … (`autoTempName`), and the run writes those names into the columns. Each row has three strengths in %: `k` = the share of an L11–20 Realm the player kills in `killSec` (100 s), `g` = the rate when grinding an L11–20 Realm for `grindSec` (280 s), `r` = the rate on L21+ in `topSec` (280 s). Common settings: the Lv1–10 Realm seconds (`realmLow`, solo), `killSec`, `grindSec`, `topSec`, the margin after a kill, and the search time (5/10/30/60 s). All of it is saved in `localStorage` (`chartmaker.auto.v1`, `power` keyed by player id), never in the txt.
  - Each row also has a Realm tier (`AUTO_TIERS`, saved as `tier` keyed by player id, default 3): 0 = no Realm (1st/2nd/3rd only), 1 = Realm up to Lv10, 2 = up to Lv20 (on Lv21+ only 1st/2nd/3rd), 3 = Lv21+ too. The % inputs a tier can't use are disabled, and `autoMask` treats them as 0, so the team sizes and the "can't reach 100%" fallback count only eligible players. Regular killers and the Lv1–10 solo Realm killer are the free player with the narrowest tier, saving wider ones for later Realms. Grinders join only bosses their tier allows, and the lookahead also checks that enough players of the right tier will be ready for each upcoming Realm. With nobody at tier ≥ 1 the run warns that 1F's Realm can't be killed.
  - `autoBuild(cfg, power, p)` is a greedy simulation that steps 1 s at a time and follows the `calc_level` rules (next-floor regulars sortie at least 1 s after the Realm kill). It sends a solo 30 s killer to each 1st/2nd/3rd, then the Realm killer(s): solo on Lv1–10, a team whose `k` values sum to ≥ 100% on Lv11–20 (`autoPickKillers`), and one player on Lv21+. Free players join the living bosses as grinders unless the lookahead (`autoUpcoming`/`autoSpare`) needs them as future killers. If the whole roster can't reach 100%, everyone grinds the Realm. Every battle ends by `CHART_SEC`.
  - `autoFill` then fills idle time (so no player sits out a whole cooldown when a battle fits). It replays the plan with the `calc_level` rules to get each boss's kill time, and builds the spans where an extra battle changes no kill time: a regular may push after the previous floor's Realm kill and must end at or after that boss's kill; a Realm grinder pushes in `[first Realm push, kill end)`, ends at or after the kill, and only on floors its tier allows; on the last floor, regulars not yet killed are open until `CHART_SEC` while no Realm has been pushed. Per player it repeatedly adds the highest-scoring battle that fits, if needed shifting that player's later grinder battles (or a killer tied with another battle ending at the same time) back within their spans, keeping the cooldown. Realm grinders on Lv11+ that would run past `CHART_SEC` are cut to the seconds left, with the rate scaled down and rounded to 2 decimals like the output. A gap can stay only when no boss the player may fight is alive in it (for example a tier-1 player while only a Lv11+ Realm is open).
  - `autoSearch` tries a grid of policies (strong/weak killers, `slack`, `kadd`, the first-sortie stagger, `joinFrom`), then hill-climbs one player's offset or one parameter at a time (mulberry32, seed 1, so runs are repeatable). It computes in 40 ms slices and yields through a `MessageChannel` (`autoYield`), because `setTimeout` is throttled to about once per second in background tabs.
  - The result reorders the columns by each player's first sortie (earliest on the left; ties and columns without battles keep their order), then gives the temporary names left to right. It replaces every block in one undo step (`replaceState`), after a confirm when the plan has battles. Names, settings, `timelag` and range notes are kept. Locks and battle notes are lost (the dialog says so), and locks are ignored by the search. 中止 stops the search and still offers the best plan found so far.
- Stats (`スタッツ` button, `#stats-dialog`, `web/stats.js`, loaded after `auto.js`; its top-level names start with `stats`/`STATS_`). It is built in the browser from `details` (`/api/detail`, matched to blocks with `detailIndex`) and `simulateFloors`, with no server change. `statsCollect` returns null while `details` is out of sync. `renderSummary` calls `refreshStats`, which re-renders while the dialog is open. Sections:
  - Cards: the expected score (and the score if every rate were 100%), the reached Lv, the battle count, and the free slots.
  - Per score band (`statsBand`: Lv1–5, 6–10, 11–15, 16–20, 21–): battles per boss, battles with rate < 1, the score and its share, and the band's time span (from the opening of its first floor to the Realm kill of its last floor, or `CHART_SEC`).
  - A cumulative score chart (SVG step line; a battle's score counts at `battle_end`, as in the tracker) with band-colored backgrounds, a tick at each Realm kill, and a hover tooltip (time, Lv, score).
  - Dead sorties (撃破後の出撃): battles whose push is at or after the kill of their boss on their level's floor and that are not the killing battle. `calc_level` still scores them, but they can't happen in the game. Each item jumps to the block (`statsJump`).
  - Per floor: opening, each boss's kill time, the duration, the battles, and the score.
  - Per player: sorties / the maximum possible from 0 s, Realm battles, the score, the first sortie, and free slots (each gap fits `floor(gap / (timelag + 300))` more sorties; the tail after the last cooldown counts while a 30 s battle still fits by `CHART_SEC`) with their times.
- Delay-sensitive kills (critical path, `web/critical.js`, loaded after `auto.js` and before `stats.js`; its top-level names start with `crit`/`CRIT_`). Computed in the browser from `details` only: `critUpdate()` runs in `fetchDetail` before `render()`.
  - For each (level, boss), the kill is the battle with the earliest `battle_end` (a tie means no single battle is critical, so it is skipped). `critRun` delays that battle's end by each of `CRIT_DELAYS` (10, 30 s) and replays the plan with the tracker's `schedule()` rules (no `RESORTIE_MARGIN`): a sortie is the latest of its push, the previous battle's cooldown end, the previous boss's kill (raw) and its own boss's open gate (shifted by the plan's own margin), a battle is skipped when its boss dies before it sorties, and kills are recomputed until nothing changes. The score is recomputed with the `generate_detail` rules (floor from the new Realm kills, rate cut past `CHART_SEC`). The loss is the base score minus the delayed score.
  - `critMap` (`"pi:ai"` → `{loss, moved, rank}`): rank 2 when the 10 s loss is at least half the largest, 1 when it is above 0. Blocks get `.crit`/`.crit-2` (a purple left stripe), and the block title and the selected-battle panel show the losses and how many sorties move.
  - `critShow` (設定 → 全般 → クリティカルパスを強調する, default on) only hides the stripe and title text. It is saved in the `localStorage` draft, never in the txt.
  - Stats has a クリティカルパス section: the top `CRIT_TOP` (10) by 10 s loss, each jumping to its block.
- The plan is to deploy publicly on Google Cloud (Cloud Run with gunicorn). Keep the server stateless.

## Progress tracker (`/tracker`, `web/tracker.*`, `store.py`)

It replaces the old in-game app that read `cleartime.json` and `detail.json`. Operators press a kill button for each boss, and every device showing the same URL stays in sync.

- The editor's 進行管理 ("progress management") button hands the current `toText()` to `/tracker` through `localStorage` (`chartmaker.tracker.text`). The setup screen reads the date and `::start_time`, then calls `POST /api/sessions {text, start_epoch_ms}` and navigates to `/tracker/<id>`. The random 128-bit id is the only access control.
- When `PLAN_BUCKET` is set, `POST /api/sessions` also saves the txt as `sessions/YYYYMMDD_<seq>_<Max>_<Est>_<session id>.txt` (same `archive_plan`, with `prefix=SESSION_PREFIX, tag=sid`; the sequence is counted per prefix). The id is in the name on purpose, to match the file with `deploy/list_sessions.py`; the bucket is private. A failed save is only logged and the session is still created.
- The server builds the plan once: `cleartime` comes from `calc_level` (index = floor; index 0 is the sentinel; trailing empty floors are trimmed), and `detail` is a trimmed `generate_detail`. Boss images that don't exist locally are dropped, because `validate(..., check_images=False)` skips the image check.
- Endpoints:
  - `GET /api/sessions/<id>?since=<version>` returns only `{version, server_now}` when nothing has changed. Clients poll every second (`POLL_MS`) and use `server_now` to correct their clock. To keep forgotten tabs from reading Firestore every second, `pollDelay` slows it to `IDLE_POLL_MS` (10 s) before `-IDLE_BEFORE` (10 min) and after `CHART_SEC + IDLE_AFTER` (30 min), and for a hidden personal view (the full board stays at 1 s during the plan because it sends the Discord notify requests). Becoming visible polls at once.
  - `POST .../kill {floor, boss}` and `POST .../undo {count}` are validated on the server with the `calc_level` rules: floor = 1 + Realm kills, and Realm is allowed only after 1st/2nd/3rd are killed on that floor. A stale or duplicate press returns 409. Before the start (`now_ms() < start_epoch_ms`, `before_start`) `kill` and `start` return 409, and the board disables the kill buttons and the `#fix-dialog` controls while `elapsed() < 0`.
  - `POST .../shift {delta}` moves `plan.start_epoch_ms` by `delta` seconds (int, non-zero; positive = later), for when the game server's clock differs. The total is kept in the doc's top-level `start_shift` (returned by the full `GET`) and limited to ±`SHIFT_MAX` (600 s). Events keep `at` and get `t` recomputed; `starts` values move by `-delta`, so kills and corrections keep their real time. Allowed before and after the start; rate-limited like `kill`. The board's `#shift-box` (-1秒/+1秒 under the clock, hidden in the personal view) posts it: a press steps 1 s at once, holding repeats after `SHIFT_HOLD_MS` (400 ms) every `SHIFT_REPEAT_MS` (100 ms), and keyboard clicks (`detail` 0) step too. `stepShift` shows the step at once (`shiftLocal`, `plan.start_epoch_ms = serverStart + shiftLocal * 1000`) and `flushShift` sends the accumulated steps as one request on release or `SHIFT_SEND_MS` (500 ms) after the last press, one request at a time, clamped locally to ±`SHIFT_MAX`. `applyResponse` takes the server start (`serverStart`) from `plan.start_epoch_ms` (full `GET`) or `start_epoch_ms` (the `shift` response) on every device (`setStartLabel` shows seconds when they are not 0 and the total shift).
  - `POST .../start {battle, t}` stores a manual sortie-time correction (see 挑戦中 below).
  - `GET .../text` returns `{text}` (the stored plan txt, for the review's JSON save; rate-limited like `kill`; 404 when the doc has no `text`).
  - `DELETE /api/sessions/<id>` discards the session (see below). `POST .../notify`, `.../notify/clear` and `.../notify/pause` belong to the Discord reminder (see below).
- `store.py`: `MemoryStore` is the default and is lost on restart. Sessions expire 5h (`SESSION_TTL`) after creation and are never extended. `get`/`update` (and `CachedStore` hits) check `expired()` and raise `NotFound`, because Firestore's TTL deletion can lag by up to a day. With `STORE=firestore`, `FirestoreStore` is used (collection `tracker_sessions`, updates in a transaction) so that several Cloud Run instances share the state. `delete` removes the doc (in a transaction for Firestore; `CachedStore` drops its cache entry) and returns the removed doc.
- `DELETE /api/sessions/<id>` (the header's セッションを破棄 button, with a confirm) discards the session: `store.delete` removes the doc and returns it, and the server then deletes any Discord messages still in `messages`. Every other device gets 404 on its next poll and `endSession` hides the board, stops the render tick and sends no more notify requests. If a session is discarded while `notify` is sending, the `remember` update raises `NotFound` and the just-sent message is deleted at once.
- There is deliberately no list API (the id is the only access control). `deploy/list_sessions.py` lists sessions straight from Firestore for the admin (`PROJECT=<id>`, needs `gcloud auth application-default login`; `--all` includes expired ones, `--url=` prints tracker URLs). `deploy/` is excluded from the container.
- 挑戦中 (fighting) and 次に出撃 (next to sortie) follow the kill buttons, not the clock. `schedule()` in `tracker.js` replays each player's battles in plan order. Each battle's actual sortie time is the latest of these:
  - its planned `push_start`
  - the previous battle's actual push + timelag + 300 + `RESORTIE_MARGIN` (1 s for the manual operation) (`readyAt`)
  - the kill time of the previous battle's boss
  - the time its own boss opened: the floor was reached (the previous floor's Realm kill), and for Realm, all 3 regular bosses on that floor were killed

  The open gate (`bossGate`) is shifted by the plan's own margin: it contributes `actual + max(0, push_start − planned gate)` (the planned gate from `cleartime`; the raw actual time when the plan has none). So a plan that opens a boss at 1:00 and sorties at 1:06 sorties at 1:08 when the opening slips to 1:02. The previous boss's kill gate is the raw kill time with no margin (it only waits for the battle to end), so a late kill doesn't delay a re-sortie that the cooldown already decides. An early kill never moves a sortie before its planned `push_start`. The editor's snap margin is not passed to the tracker: it is already in the plan. An unresolved gate leaves the battle not `known` and records `wait` (`<boss> 討伐待ち`, `LV<n> 開放待ち`, `3体討伐待ち`), inherited by later battles.

  Manual corrections override this: `starts` (`{str(detail index): elapsed seconds}`, doc top level, returned by the full `GET`) replaces a battle's `at` and makes it `known` (`fixed`), and later battles of that player follow from it. `POST /api/sessions/<id>/start {battle, t}` sets it (`t` an int in `START_RANGE` −3600–7200 (negative because 出撃可能にする in the first 5 minutes puts the start before 0), or `null` to remove; bools are rejected; 400 otherwise; rate-limited like `kill`).

  It uses the `level` field in `detail` to know the floor, so a delay carries over to every later battle. A battle stays 挑戦中 until its boss's kill button is pressed, and shows `N秒 超過` (N s over) once it passes its planned duration. A battle whose sortie time has passed but whose gate is still closed shows 待機中 (waiting) in 次に出撃. A battle whose boss was killed before it sortied is skipped (except a `fixed` one). 次に出撃 (`nextBattles`) lists every waiting/upcoming battle from the current stage up to the stage after next (`stageOf`: floor n's 1st/2nd/3rd is stage 2(n−1), its Realm 2(n−1)+1; the current stage is the current floor's Realm once its 3 regular bosses are killed). So on 1st/2nd/3rd it shows the same floor's Realm and the next floor's 1st/2nd/3rd, and on Realm the next floor's 1st/2nd/3rd and Realm. A player can appear more than once, each row with its `LV`.
- Notes: `POST /api/sessions` reads them with `parse_notes` (bad ranges, empty or > 200-char text, or > 50 range notes are 400). Battle notes go into `detail[i]["note"]` (the index is the action-line order, which equals `generate_detail`'s order) and range notes into `plan.notes`. The board's `#notes-box` (above 挑戦中, hidden when empty) lists battle notes while the battle is `upcoming` with `at - now <= lead`, `waiting` or `fighting`, and range notes exactly while `start <= elapsed() < end` (battle notes use `lead` = `plan.notify_lead`, or `NOTE_LEAD` = 30 s without Discord). The 挑戦中 and 次に出撃 rows also show the battle's note (`rowNote`).
- 出撃タイマー (sortie timers, `#timers` below 挑戦中/次に出撃): one card per player in chart column order (`buildTimers`, `renderTimers`). `playerStatus` gives the latest started battle (fighting or done), the fighting one and the next one. A card shows `挑戦中 <boss>` with the re-sortie countdown while it is above 0 (at 0 or below it shows 出撃可能 even if the boss's kill hasn't been pressed: 出撃可能 means countdown ≤ 0), or the countdown to `readyAt(started)` with a progress bar, then a green 出撃可能 with the next boss and its estimated time (or its `wait` reason), or 作戦終了. ✎ marks a corrected battle. Clicking a card opens `#fix-dialog` (re-rendered on every tick), which shows the card's countdown and has only two controls, both moving the latest started battle (fighting or done): 出撃可能にする (countdown to 0, then closes the dialog) and ±1/5/10/60 s on the shown countdown (+ from 出撃可能 counts from now; − at 出撃可能 does nothing). `setLeft(left)` posts `t = floor(elapsed() + left − (readyAt − at))`, the integer start that makes the card's `ceil(readyAt − now)` show exactly `left`. All go through `act("start", …)`, so every device shares them. They move the latest started battle, or the next battle when the player has not sortied yet (`fixTarget`; it then becomes 挑戦中). `setLeft` caps the countdown at the cooldown, so the corrected start is never in the future. A corrected (`fixed`) battle is never turned into `skip` by an earlier kill, so + on a done battle keeps it as the latest started one. The server still accepts `t: null` (remove the correction), but the UI no longer sends it.
- Plan chart (作戦チャート, at the bottom of the board): `POST /api/sessions` also stores the txt at the doc top level (`text`, never returned by `GET`). `GET /api/sessions/<id>/chart.png` renders it with `render_png` on first access and keeps it in `ChartCache` (in-process LRU, `CHART_CACHE` = 8 sessions; dropped on `DELETE`), with `Cache-Control: immutable`. Only a cache miss goes through `LIMIT_RENDER` and `render_slots`, and it never calls `archive_plan`. The PNG (0.3–1.4 MB) is too big for a Firestore doc, so it is not stored. Sessions without `text` get 404 and the section stays hidden. `renderChart` in `tracker.js` overlays `schedule()` on the image with %-positioned boxes, using ChartLib's fixed layout (column `120 + i*246`, width 240, y = seconds + 160; `i` is the first-appearance order of `raw_name` in `plan.detail`, `plan.column`): fighting blinks (red when overdue), done/skip is darkened from `push_start` down to its cooldown end (`battle_start + COOL_TIME`, the chart's `cool_off`; other boxes end at `battle_end`), the 次に出撃 battles (`nextBattles`, shared with the list) get a dashed outline, and `.chart-now` marks `elapsed()`. Clicking the chart toggles fit-to-width and actual size. The team/name band (the image's top `CHART_HEAD` = 140 px: the party dots end at y≈130 and the `60:00` grid label starts at y≈148) stays pinned like a frozen row in Excel: `#chart-head` is a sticky copy of the same image, cropped by a `ResizeObserver` on the main img to the band's displayed height, and `.chart-wrap` gets the same negative `margin-top` so the two overlap exactly when not scrolled. Don't put `loading="lazy"` on the img: it sits in a hidden section and would never load.
- Review (振り返り, `web/review.js`, loaded after `tracker.js`; its top-level names start with `review`/`REVIEW_`): the header's 振り返り button opens `#review-dialog`, built in the browser from `events` and `tracker.js`'s `planned`/`killTime`/`bossGate`, with no server change except `GET .../text`. For each kill: 差 = kill time − `planned(floor, boss)`, and 増えた遅れ (`added`) = 差 − (`bossGate` actual − planned), i.e. the delay that arose on that boss, not the one carried in. Kill times are button-press times. Sections: cards (kills and reached LV, the latest kill's 差, the largest 差), a per-floor table (opening, each boss's kill with (±差) and the planned time in the title, duration; floors not reached collapse into one dim row), an SVG delay chart (hover tooltip), the top `REVIEW_TOP` (10) bosses by `added` plus the 3 most negative (遅れを取り戻したボス), each jumping to its table cell. `render()` calls `reviewRefresh()`, which redraws only while the dialog is open and `events` changed. JSON で保存 downloads `YYYYMMDD_review.json`: `{kind: "chartmaker-review", version: 1, start_epoch_ms, saved_at, events, starts, plan: {cleartime, detail (without id), notes}, text}` (`text` null when the session has none). Hidden in the personal view; `endSession` hides the button and closes the dialog. The setup screen's 振り返りファイルを開く (`#review-file`) reopens a saved file without a session: `reviewParse` validates it (kind, `version` ≤ 1, events), and `reviewOpenFile` replaces `tracker.js`'s `plan`/`events`/`starts` and shows the same dialog (title with the start date, save button hidden). The close/save/file handlers are wired once at the end of `review.js`, because `init()` runs before `review.js` is loaded. `planTextOf` (`common.js`) lets both テキストを開く buttons (editor `#file-open`, tracker `#setup-file`) accept a review JSON and take its `text` (an error when it has none).
- Personal view (`/tracker/<id>?p=<raw_name>`): a read-only page for one player, mainly on a phone. `buildBoard` checks `personal` (the `p` query) and calls `buildPersonal` instead of `buildChart`/`buildPeople`; `body.personal` hides the boss buttons, lists, timers, history, chart, score and comment, and the header hides discard, notify pause and 個人ビュー but shows 全体を見る. `#me-select` picks the player (`setMe` keeps `?p=` and the page title in sync; an unknown name shows the picker). `renderMe` shows a big card (挑戦中 with the time left or `N秒 超過` and the re-sortie countdown, 出撃待ち with the `wait` reason, the countdown to `next.at`, green within `noteLead()`, or 作戦終了) and the player's battles from `schedule()`. Battle notes in `#notes-box` are filtered to that player; range notes still show. It sends no kill/undo/start/notify requests (`notifyUpcoming` runs only on the full board) and never loads the chart image. On the full board, the 個人ビュー button opens `#people-dialog`, which lists each player's URL with 開く/コピー and a copy-all (`name URL` lines).
- "作戦との差" (difference from the plan) is the larger of: the last kill's delay against `cleartime[floor][boss]`, and the overdue time of any pending boss on the current floor. Late is red and early is green. The score is the sum of `est_score` over battles with `battle_end <= now`.
- Quirk inherited from `calc_level`: a regular-boss battle with `push_start == 0` is not counted toward 1F (`push_start > clear_time[0]["Realm_boss"]`), so a plan whose first pushes are at second 0 shows "作戦に予定なし" ("not in the plan") for 1F.
- Discord reminder (optional, read aloud or plain text): the setup screen takes a Discord webhook URL, a lead time (`notify_lead`, 5–120 s, default 30) and a 読み上げる (TTS) checkbox (`notify_tts`, bool, default true). The URL and the checkbox are remembered in localStorage (`chartmaker.tracker.webhook`, `chartmaker.tracker.tts`). Text-to-speech is done by the Discord clients, not the server: the message is sent with `tts: discord.tts`, so turning it off sends the same text as a plain message. Sessions created before the option have no `tts` key and still read aloud.
  - `POST /api/sessions` accepts only URLs matching `DISCORD_WEBHOOK` (SSRF guard), else 400. The webhook is stored at the doc top level (`discord = {webhook, lead, tts}`, `notified = []`), never inside `plan`, so `GET` does not leak it. `plan.notify_lead` holds only the seconds and `plan.notify_tts` the flag (both null when off); the board header shows which mode is on.
  - The server has no timers (min-instances=0). `notifyUpcoming` in `tracker.js` fires once any `upcoming` battle not yet sent by this tab (`notifySent`) has `at - now <= notify_lead`. It then POSTs `.../notify {battles}` (`plan.detail` indexes) for every such battle with `at - now <= notify_lead + NOTIFY_GROUP` (5 s), so players sortieing together are called in one message. It ignores `known`: `at` is then the earliest possible sortie (the plan time and cooldown, ignoring unresolved kill/floor gates), so the call goes out on schedule even if the current boss is still alive. The server records the indexes in `notified` inside the transaction, so every open device may ask but each battle is announced once (a request whose battles and notes are all already recorded is answered from a `store.get` without a write, so the other devices' identical requests don't bump `version`) (`sent` lists the newly announced ones; up to `MAX_NOTIFY_BATTLES`; any bad index is a 400). No notifications if nobody has the tracker open.
  - `send_discord` (urllib, 5 s timeout) runs after the transaction. A failure is only logged and never retried, except a 429 (webhook rate limit), which waits `retry_after` (at most `DISCORD_RETRY_MAX` = 3 s) and retries once. The message is `<name>、<name>、準備して下さい` (the newly announced battles' names, deduplicated) with `allowed_mentions: {parse: []}`, so a name containing `@everyone` pings no one. 409 without a webhook.
  - Notes in the call: battle notes of the newly announced battles are appended (`A、B、準備して下さい。A: <note>。B: <note>`). Range notes are announced as their own message `注意: <text>`: `notifyNotes` in `tracker.js` POSTs `.../notify {notes: [plan.notes indexes]}` at the start time (`start <= now < min(end, start + NOTE_SPEAK)`, `NOTE_SPEAK` = 30 s, so a tab opened later doesn't announce stale notes), and `.../notify/clear {note}` once `now >= start + NOTE_SPEAK`, when the speech is over (`noteSent`/`noteCleared`). `notify` accepts `battles` and/or `notes` (at least one); the server dedupes notes with `notes_notified` (missing in older sessions, so `setdefault`), stores their message ids as `messages["n<index>"]`, and returns `notes`. Pause applies to notes too. `send_and_remember` truncates content to 2000 chars.
  - Discord's TTS reads only 50 characters of a message and says 「以下略」 for the rest. So with TTS on, `send_and_remember` splits the content with `split_tts` into parts of at most `TTS_MAX` (50) chars (after 、。，,．！？!? first; a sentence still too long splits at whitespace, then by character count) and sends them one by one, at most `TTS_PARTS_MAX` (10) (the rest is dropped and logged). A failed part stops the rest. Plain-text mode (`tts` off) sends one message. The entry in `messages` keeps the first part's id as `id` (the group key used by `notify/clear`) and, when split, every part's id in `ids` (`message_ids`), so clear, the stale sweep, `DELETE` and the discarded-while-sending case delete all parts; `cleared` counts Discord messages.
  - The message is deleted again so the channel log doesn't fill up. `send_discord` posts with `?wait=true` and returns the message id, which a second `store.update` saves in `messages[str(battle)] = {id, at}` for each battle in the group (same id). Once the battle leaves `upcoming` (its sortie time, so the speech has finished), `notifyUpcoming` POSTs `.../notify/clear {battle}` once per tab (`notifyCleared`). The server pops every entry with that battle's message id (a grouped message goes when its first battle sorties) plus any older than `MESSAGE_KEEP` (max lead + 60 s, a sweep for missed clears) in a transaction, then calls `delete_discord` (`DELETE {webhook}/messages/{id}`; failures are only logged). It checks `store.get` first and skips the write when there is nothing to delete, because every `update` bumps `version`. Deletion also needs an open tracker.
  - Pause: the board header's 通知を止める / 通知を再開 button (confirm only when stopping) POSTs `.../notify/pause {paused}` (409 without a webhook), which sets the doc's top-level `notify_paused` for every device; the full `GET` returns it. While paused, `notifyUpcoming` sends nothing (clears still run), and the server's `notify` returns `sent: []` without recording `notified`, so after resuming, battles still `upcoming` within the lead are announced.
  - Discord-side limits: only users viewing that channel in the desktop client hear it, and each must allow /tts playback (User Settings → Accessibility → Text-to-speech). Mobile does not read it aloud.

## Deploying to Cloud Run (`Dockerfile`, `deploy/`)

Run these from the repo root in Git Bash, with `PROJECT=<id>` set:
- `deploy/setup.sh` runs once. It enables the APIs, creates Firestore with a TTL on `expire_at`, and creates the `chartmaker-run` service account with `roles/datastore.user`. It also creates the plan bucket (`PLAN_BUCKET`, default `chartmaker-output`) if missing and grants the service account only list + create on it (`objectViewer`, `objectCreator`), so the app cannot overwrite or delete saved plans.
- `.gcloudignore` only does `#!include:.dockerignore`, so edit the exclusions in `.dockerignore`.
- `deploy/deploy.sh` runs `gcloud run deploy --source .`. It uses `--max-instances` (default 1, which is the main cost cap), `--min-instances=0`, `--concurrency=32`, `STORE=firestore`, and `PLAN_BUCKET` (default `chartmaker-output`; `PLAN_BUCKET=` disables saving), and `SUPPORT_URL` (default the OFUSE page; `SUPPORT_URL=` hides the link). The env vars are passed with gcloud's `^@^` delimiter so a URL may contain commas. It also sets an Artifact Registry cleanup policy (keep the 2 newest images) and a lifecycle rule that deletes the uploaded source zips in `gs://run-sources-<project>-<region>` after 7 days.
- `deploy/budget.sh` creates a budget (default `BUDGET=1000JPY`) that publishes to Pub/Sub topic `billing-alerts`. The `stop-billing` function (`deploy/billing_guard/`) unlinks the project's billing account once cost exceeds the budget. Set `DRY_RUN=1` to deploy it in log-only mode.

The cost guards inside the app are per-process:
- `RateLimiter` limits requests per IP (`LIMIT_*` in `app.py`). On Cloud Run the client IP is the last `X-Forwarded-For` entry.
- `render_slots` caps concurrent renders at 2, and returns 503 after a 20 s wait.
- `CachedStore` reuses a Firestore `get` for 1 s, so tracker polling costs about 1 read per second per session per instance, instead of 1 per client.

gunicorn runs 1 worker × 16 threads, so these guards share one process.

## Plan-writing skill (`.claude/skills/raid-plan/`)

A Claude Code skill for writing plans by hand with Claude, independent of the app. `scripts/simulate.py` is a standalone (stdlib-only) mirror of `parse`/`calc_level`/`generate_detail` that reports the score, floor clear times, errors and idle gaps; keep it in sync with ChartLib when the rules change. The `references/*.md` files are written by the user. `.claude/` is excluded from the container.

## Input schedule format (`src/*.txt`, parsed by `parse`)

- A line starting with `#` is a comment.
- `::key=value` defines a constant. A bare `::key` sets that key to `None`, which is how the presence-only flags are turned on. Constants are merged over `config.json` (`setting = dict(config, **constants)`). Values stay strings, so numbers like `::timelag=3` are converted with `int()` at the point of use. Constants the chart relies on:
  - `::1st_boss=`, `::2nd_boss=`, `::3rd_boss=`, `::Realm_boss=` set each boss's element color (`blue`, `red`, `green`, `yellow`, or `white`). These are required because `setting[action]` is looked up for every battle.
  - The flags `display_party`, `display_boss`, `display_team`, and `display_remaining` are checked by presence only. `display_remaining` makes the per-battle time labels show the time left in the 60 minutes instead of the elapsed time. `format_clock` renders it, and shows `-mm:ss` past the end. The GUI's `clock()` mirrors this, including the timeline axis and the push-time input.
  - `image_1st`, `image_2nd`, `image_3rd`, and `image_realm` give the boss icon paths used when `display_boss` is set, for example `/image/LI_4002011.png`. The images can be any size or aspect ratio: `load_boss_icon` crops the centre square and resizes it to 100×100, keeping the alpha channel (premultiplied, so edges don't darken). `flatten_boss_icon` composites the icon over the chart already drawn beneath it, so transparent areas show the battle's boss color down to `battle_end` and the cooldown gray (or the score-rate checkerboard) below that. The optional `::icon_bgcolor=<color_table name>` instead fills transparent areas with a single color for every icon.
  - `::<player_id>=<display name>` sets a player's display name.
  - `::start_time=HH:MM` is the game's local start time, used only by the progress tracker. ChartLib ignores it, and the PNG is unchanged.
- An action line has the form `player_id,wait_seconds,boss,battle_seconds[,score_rate][,lock|unlock[,note]]`. `split_action` splits it: a 5th field that is a number (`RATE_RE`: ASCII decimal, optional sign and exponent; so `nan`, `inf` and full-width digits are not numbers) is the rate, and an empty 5th field is an omitted rate. The next field, if it is `lock`/`unlock` (case-insensitive), is the lock word. Everything after that, up to the end of the line, is the note (it may contain commas, and a `lock` inside it is just text). So extra fields are never a parse error, and a misspelt rate or lock word becomes a note. Trailing empty fields are ignored. `toText()` still writes `,unlock,<note>` before a note-only line, so a note that looks like a number or a lock word reads back the same. `RATE_RE` is mirrored in `web/app.js` (`splitAction`) and `simulate.py`. The lock and the note are editor/tracker data only; `parse` returns just the first 5 fields, so the chart is unchanged. The older `#lock` / `#note <text>` comment lines after the action line are still read and override the inline values.
  - `boss` must be one of `1st_boss`, `2nd_boss`, `3rd_boss`, or `Realm_boss`.
  - `wait_seconds` is added to that player's running clock before the push. Each push then advances the clock by `timelag + 300` (the cooldown).
  - `score_rate` defaults to `1.0`. A number so large that it becomes `inf` is replaced with `1.0` by `parse`. A value below 1 draws a checkered pattern and a percentage on the battle.
  - A player ID has the form `<Team><2 chars>`, for example `Alpha01`. The team name is `raw_name[:-2]`, and team colors come from `config.json` → `team.team_color`.

## Architecture (`ChartLib.py`)

The pipeline is `generate_chart` → `parse` → `generate_detail` → `calc_level`, then drawing.

- `calc_level` simulates floor progression. The three regular bosses must be cleared on the current floor before a `Realm_boss` clear advances to the next floor. It returns the clear time of each floor. `generate_detail` uses these times to assign each battle its `level`, and the level sets the score: `50000 * min((floor-1)//5+1, 5)`, times 1.2 for the Realm boss.
- Drawing happens in layers, all from one `generate_detail` result:
  1. OpenCV draws the battle and cooldown blocks behind the grid.
  2. OpenCV draws the grid and time labels.
  3. OpenCV draws the text labels in front of the grid.
  4. The image is converted to PIL for the Japanese-capable text (player and team names, the comment, in `font/NotoSansJP-Regular.otf`, SIL OFL 1.1, license in `font/OFL.txt`).
  5. The image is converted back to OpenCV for the party dots and the logo.
- The y positions of the time labels (battle start, battle end, `Nsec` duration, re-sortie time) come from `layout_time_labels`. For each player column it spreads the labels apart so they keep a minimum spacing while moving as little as possible from their default positions (least squares). This stops labels overlapping when a battle is very short or when blocks sit right next to each other.
- Layout constants are hardcoded. Columns are 246 px wide starting at x=120, with a maximum of `MAX_PLAYERS` (20) players. `margin_top` is 160, and y = seconds + `margin_top`. The score footer is at y≈3840–3980.
- All colors in `config.json` are in **BGR** order, because the arrays are OpenCV arrays and the PIL fills are written straight into them.
- Many draw calls read `config[...]` instead of `setting[...]`. A `::` constant in the txt file overrides only the keys read through `setting`: timelag, boss colors, the display flags, images, fonts, the comment, and the logo.
